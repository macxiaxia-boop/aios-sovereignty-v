### 4 类根因（按出现频次）

#### 类别 1 · worker 没到 crash hook (3 cases: CR3, CR5, CR8)
- **现象**: `worker did not reach crash_after_* hook`
- **原因**: 
  - CR3 (`plan_revert` mode): 工人代码本身没真正触发 `crash_after_old_inactive` 分支 — `session_scope` 第一个 block 已 `await session.commit()` 把 `v1` 写入；第二个 block 的 `mark_inactive` 没在 `crash_hook` 检查前触发
  - CR5/CR8 类似
- **修复**: 需要重排 `_plan_revert` / `_budget_check` 等 worker 函数，让 `crash_hook` 检查在写入之前

#### 类别 2 · evidence count = 0 (3 cases: CR4-CR7 cleanup path)
- **现象**: `expected exactly 1 evidence after clean run; got 0`
- **原因**: 
  - `_verifier_call` worker 第 386-400 行：`async with session_scope(factory) as session: ... await repo.add(ev); return {...}` — `return` 在 `async with` 内退出，但 Python 的 `async with __aexit__` 应该正常 commit
  - 但实测 DB 中 evidence 0 条 → 说明 commit 没生效
  - 可能原因：`SqlAlchemyRepository.add()` 使用 `session.merge(orm_obj)` — `merge` 在 `async with` 退出前可能没有 flush 到 DB（autoflush 默认 False for SQLAlchemy async）
  - 同样 `_evidence_write`, `_budget_check` worker 都有此模式
- **修复**: 在 `await repo.add(ev)` 后加 `await session.flush()` + `await session.commit()`，或改用 `session.add()` 替代 `merge`

#### 类别 3 · verify_state 缺 `workflow_run` key (1 case: CR10)
- **现象**: `KeyError: 'workflow_run'` in `state_pre["workflow_run"]`
- **原因**: 
  - `verify_state` worker line 695-699: `if run_id: run_row = await session.get(WorkflowRunRow, run_id); if run_row: result["workflow_run"] = {...}`
  - 当 `run_row` 为 None 时，`workflow_run` key 不写入 result
  - 但 CR10 先跑 `workflow_run` worker，`engine.start()` 第 91-94 行 `await insert_run(); await session.commit()` 应该已提交
  - 可能原因：SQLite async commit 时机问题，或者 `db_url` 在 worker 间传路径不一致（fixture 是 tmp dir）
- **修复**: 改 `verify_state` worker，给 `workflow_run` key 设默认空 dict（即使 row 找不到）

#### 类别 4 · DB disconnect / restart (1 case: CR9)
- **现象**: 重连后 panic / 空 DB / leaked connection
- **原因**: `aiosqlite` 引擎 dispose 后需要重新 `init_schema`，但 worker fixture 没显式调
- **修复**: 在 `injector.start_kernel` 第二次启动时显式 `engine.init()`（PGCheckpointerEngine.init() 已经在调用）
