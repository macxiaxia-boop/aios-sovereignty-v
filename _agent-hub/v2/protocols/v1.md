# AIOS Hub v2 · Protocol v1 (Bidirectional)

> **Status**: active (R320 2026-09-29)
> **Schema**: `v2/schemas/envelope.schema.json`
> **SSOT**: this file + the JSON Schema it points to.

## 1. Goals

1. One canonical **direction** (Codex / Claude Code / WorkBuddy / Hermes / OpenClaw can all send AND receive).
2. Versioned envelope so future v2.x can evolve without breakage.
3. Machine-validatable (JSON Schema + idempotency_key dedup).
4. Audit-friendly: every transition is appended to `v2/logs/events.ndjson`.

## 2. Topology

```
v2/
├── messages/
│   ├── inbox/     # envelopes awaiting processing (one .json per envelope)
│   ├── outbox/    # envelopes produced locally (audit trail)
│   └── deadletter/# envelopes that exceeded retry or schema-failed
├── tasks/         # one .json per task_id; state machine file
├── runs/          # one .json per (task_id, attempt_no)
├── logs/events.ndjson
└── state/state.json   # aggregate snapshot (rebuilt from tasks/)
```

`inbox/` and `outbox/` are shared across all 5 agents. Each agent must claim messages it intends to consume via a sibling `<envelope>.claim` file. A successful claim becomes `<envelope>.done` or simply `os.remove(<envelope>)`.

## 3. Envelope (v1.0)

See `schemas/envelope.schema.json`. Required fields:

| field | type | notes |
|---|---|---|
| `id` | uuid4 | unique envelope id |
| `schema_version` | string | "1.0" |
| `message_type` | enum | `message` \| `task` \| `status` \| `result` \| `ack` \| `heartbeat` \| `error` |
| `sender` | string | agent_id |
| `recipient` | string | agent_id or "broadcast" |
| `timestamp` | ISO8601 | UTC, e.g. `2026-09-29T12:00:00Z` |
| `idempotency_key` | sha256 hex | canonical `sender|recipient|message_type|json(payload, sort_keys=True)` |
| `payload` | object | depends on message_type |

Optional: `correlation_id`, `in_reply_to`, `artifact_refs[]`, `retry_count`, `ttl_ms`.

## 4. Message Types

| type | sender | payload contract |
|---|---|---|
| `message` | any | `{text: string, subject?: string}` |
| `task` | orchestrator | `{task_id, title, description?, timeout_ms, max_retries}` (must reference a task in `tasks/`) |
| `status` | executor | `{task_id, state, progress_pct?, note?}` |
| `result` | executor | `{task_id, output_payload}` |
| `ack` | any | `{ack_of: <envelope_id>, note?}` (terminal acknowledgement) |
| `heartbeat` | any | `{agent_id, status: "alive"\|"stale"\|"dead", current_task_id?}` |
| `error` | any | `{code, message, details?}` |

## 5. State Machine (Task)

```
queued ──claim──▶ running ──heartbeat──▶ running
   │                  │
   │                  ├──done──▶ succeeded
   │                  ├──fail──▶ failed ──retry──▶ queued (retry_count < max_retries)
   │                  └──timeout──▶ failed
   └──cancel──▶ cancelled
```

- A `running` task must `heartbeat` within `timeout_ms / 3` (default 20s of 60s).
- A `running` task whose `heartbeat_at` exceeds `lease_expires_at` is reaped to `failed`.
- A `failed` task with `retry_count < max_retries` is auto-requeued with `retry_count++`.

## 6. Concurrency

- All state-mutating writes go through `src/queue.py` and `src/state_machine.py`.
- Each `tasks/<task_id>.json` write takes an OS file lock (`portalocker`-equivalent; we use a portable `fcntl`-style `msvcrt` lock on Windows and `fcntl.flock` on POSIX).
- Envelope dedup uses `idempotency_key` index in `state/state.json::counters.idempotency_hits`.

## 7. Idempotency

- Producer computes `idempotency_key = sha256(canonical(sender|recipient|message_type|payload))`.
- Consumer rejects duplicates (returns existing `id` instead of new one).
- Enables safe retry across CC sessions.

## 8. Audit

Every state-changing call appends one NDJSON line to `logs/events.ndjson`:

```json
{"ts":"2026-09-29T12:00:00Z","actor":"claudecode","event":"envelope.enqueue","envelope_id":"...","message_type":"task","recipient":"codex"}
{"ts":"2026-09-29T12:00:01Z","actor":"supervisor","event":"task.transition","task_id":"...","from":"queued","to":"running"}
```

## 9. Backwards Compat

- `v2/` is additive. `_agent-hub/**` (the markdown SSOT) is unchanged.
- `sync-from-hub.ps1` continues to work for the original markdown sync.
- A new `cli/aiosv2.py` is the primary user-facing entry.

## 10. Ack Routing (R320.6)

### Why this section exists

A real two-process round-trip (Codex → CC → ack → Codex) exposed a gap:
prior to R320.6, `cmd_ack` wrote the ack envelope to `outbox/`, but
`receive` only reads `inbox/` and there is no outbox→inbox dispatcher.
So the ack was un-deliverable. R320.6 closes the gap and pins the new
contract here so it does not regress.

### The rule

> **`cmd_ack` MUST write the ack envelope to `inbox/` (recipient =
> original.sender) by default. Outbox is audit-only.**

- `inbox/` is the **delivery queue**. Anything written there is visible
  to `receive --agent <X>` once its `recipient` matches.
- `outbox/` is an **audit trail**. There is no dispatcher, no watcher,
  no transport that copies outbox → inbox. Anything written to outbox
  is *not* visible to `receive` from another process.
- The CLI `ack` command defaults to `--dest inbox`. `--dest outbox` is
  available as an explicit audit-only override and MUST NOT be used to
  attempt delivery.
- The ack envelope is built via `envelope.reply_envelope(original, ...,
  message_type="ack")`, which guarantees:
  - `recipient == original.sender`
  - `correlation_id == original.id`
  - `in_reply_to == original.id`

### No ack-of-ack loop

The protocol does not require ack-of-ack. After A receives B's ack,
the system is in steady state. The CLI does not auto-emit any further
envelope when an ack is received. If a process manually calls `ack` on
the ack envelope, that creates a new ack envelope — but this is a
deliberate user action, not protocol-required behavior, and the test
suite verifies the steady-state invariant.

### Send-time correlation metadata

R320.6 added two optional CLI flags to `send` so a caller can mark a
result/status/error envelope as a reply without going through the
`reply_envelope` helper:

```text
aiosv2.py send --from A --to B --type result \
    --payload '{...}' \
    --correlation-id <original_env_id> \
    --in-reply-to <original_env_id>
```

Omitting either flag preserves R320 / R320.1 behavior (envelope has no
`correlation_id` / `in_reply_to` field).
